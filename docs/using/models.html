Working with Omnissiah

Models

Omnissiah has no models of its own. You link one or more yourself, and after that they sit in the same model picker, cloud and local mixed together.

Cloud models

Go to Settings → Models, pick the provider under Add an API (cloud) model, paste your API key and click Add. The key is checked with the provider right away, so a typo shows up at the moment you make it.

Your keys are read server-side only and never reach the browser. You pay the provider directly; what a conversation cost is shown in the statistics dashboard.

Your own endpoint

If the service you want is not in the list above, you link it yourself. That works for OpenRouter, Groq, DeepSeek, a gateway at work, or anything else that speaks one of the two common API formats.

Go to Settings → Models → Your own endpoint and fill in:

  • a name you recognise, for example "OpenRouter";
  • the base URL, for example https://openrouter.ai/api/v1. Mind the path: with most services the /v1 belongs to it;
  • the API format: OpenAI-compatible (default) (by far the most common) or Anthropic;
  • optionally an API key. That one is optional: a server on your own network without a login works just as well without.

With Test you check whether the endpoint is reachable and how many models it offers, before you save anything. After that those models appear in the model picker under the tab Endpoints, with the name of your endpoint underneath.

Pick the format the endpoint speaks, not the brand name of the model. The app says it right there: "Choose what the endpoint speaks, not the brand name of the model." That sounds obvious and is not: OpenRouter offers models called anthropic/claude-…, for instance, but they simply talk in the OpenAI format. The brand name in the model name says nothing about the format of the service offering it.

If your gateway speaks both formats, you add it twice, once per format.

What your own endpoint does not get

  • Costs are not calculated. Omnissiah does not know the rates of your endpoint, and an amount of 0 would suggest it was free. Instead it says "not calculated", in Statistics too. Tokens are still counted.
  • No adjustable thinking phase. The Effort row is missing: which levels your endpoint knows and how you drive them differs per service, and offering something that might do nothing is worse than leaving it out.
  • No prompt caching. If your endpoint points at Anthropic, the same turn is cheaper there through the ordinary Anthropic link above. Your own endpoints are for what is not in there yet, not as a detour to what already is.
  • If you point your own endpoint at a local server you could also link directly (Ollama, LM Studio), that is allowed, but the app says so: through this route it misses measuring the context window, loading a model and managing models.

What a model promises, and what it proves

Of the models in the list above, Omnissiah knows what they can do; that is maintained by hand. With your own endpoint it depends on what the service publishes itself, and you see that back in the detail panel:

  • "Properties read from this endpoint" - the service reports per model what it can handle. If a model does not support tools, Agent and Research are greyed out, with the reason.
  • "Properties not reported; these are assumptions" - the service says nothing. Then nothing is blocked, but nothing is promised either: you see "Tool support unknown - this server does not report what the model can do" instead of a tick that merely looks like certainty.

Local models

Besides the cloud you can run models on your own machine: free, private, no key. Omnissiah talks to any server that speaks the OpenAI-compatible API; the best known is Ollama, and LM Studio works too.

Connecting. Install Ollama and usually that is all. If it runs on the same machine, Omnissiah finds it by itself: Settings → Models then shows "Ollama found at …" with a Connect button. By hand works too, by filling in the base URL and clicking Connect.

Fetching models. Click Discover models (in Settings → Models, or at the bottom of the model picker). There you search the GGUF models on Hugging Face, look at the details, parameters, context length, capabilities and README per model, and download a quant variant straight to your local server, with a progress bar. The model then appears in the model picker by itself. A 4-bit variant such as Q4_K_M is usually the best balance between size and quality, and the app says so with the choice.

If you prefer the terminal, that works too (ollama pull llama3.1); with Test again you then refresh the list in the app.

Which URL

  • Desktop app, or the web version through Node on the same machine: http://localhost:11434. Usually found automatically.
  • Web version in Docker: http://host.docker.internal:11434, so the container reaches the Ollama on your host. On Linux you need to add extra_hosts: ["host.docker.internal:host-gateway"] to docker-compose.yml for that.

Will this model fit on my machine

With every quant variant in Discover models there is an estimate, based on the memory you entered under Settings → Models:

  • Full GPU offload possible - estimated to fit entirely in your GPU memory, the fastest way to run.
  • Partial GPU offload possible - fits partly; the rest runs on the CPU. Often works fine, but is noticeably slower.
  • Probably too large - larger than the memory of your machine. Loading may fail or the model becomes very slow.

It stays an estimate based on file size and memory; the architecture and the context length of the model can change the picture. Variants you already have are marked as installed, and deleting can be done from the same screen.

Two things are not possible. Models with a licence you have to agree to first ("gated", such as Meta Llama) you can only fetch after doing that on huggingface.co. And variants consisting of several files (sharded GGUF) cannot be downloaded by Ollama yet; they carry the label "split", so pick another variant.

The context window of your local server

This is the pitfall that bites most people, and it is not visible on the model.

A model may handle an enormous context window, but Ollama loads it at 4096 tokens by default. That is enough to chat and too tight for agent mode: there all the descriptions of the tools join the prompt, and with a linked folder you are over it in no time. The turn then stops immediately, with a message that shows the text of your server literally ("request (5168 tokens) exceeds the available context size (4096 tokens)").

You raise it on the server side, not in Omnissiah:

  • Ollama app: settings → Context length up, for example to 16k or 32k.
  • Ollama through the terminal: start it with OLLAMA_CONTEXT_LENGTH=16384 ollama serve.

A bigger window costs more memory, so do not set it higher than your machine can take. Omnissiah measures for itself which window your server uses and reckons with that: the context ring in the header shows the real percentage, and the sources threshold takes it into account. So you do not have to set anything in the app, only restart your server after the change.

Good to know

  • Bigger models, from roughly 8B, work best with tools and agent mode. Models without tool support can simply chat: Omnissiah then leaves the tools out automatically.
  • If an answer dies halfway, Omnissiah reports it with "Answer truncated: this model's output limit was reached". With local models that limit is derived from the context window, so a bigger window solves that too.
  • The official GGUF repos of some makers, Mistral for instance, are not compatible with Ollama. Pick a community variant then, such as those from lmstudio-community or bartowski. The error message in the app points you there as well.
  • Local models cost nothing, and appear in the statistics dashboard at $0.
  • A token is only needed if your local server sits behind authentication. Ollama does not have that.

The model picker

The model applies per conversation, and a new conversation starts with the model you picked last. There is no "default model" setting: that could point at a provider you no longer have a key for.

At the top the picker has a search field that searches on name, maker, quant variant and model id, and below it the filters All, Local, API and Endpoints. Providers without a key or without a connection are not in it: a model you cannot pick anyway is noise.

Move over a model and a panel with the details appears. With a cloud model: provider, context window, maximum output, the price per million tokens in and out, when it was released, and what it can do (Extended thinking, Vision, PDF input, Structured output, Code execution, Citations). With a local model: family, parameters, quantization, context length, size on disk, and "Price: free (your own machine)". If your local server cannot supply metadata, it honestly says "specifications unknown" instead of an invented number. With a model from your own endpoint the name of that endpoint is shown, plus "Price: not calculated".

Switching mid-conversation is allowed and the conversation simply carries on with the new model. There is a price tag, and the picker names it: "Switching models invalidates the prompt cache: the next turn charges ~12.4k tokens in full again." Another model is another cache, with every provider. At the start of a conversation there is nothing to invalidate and that line stays away.

How deeply a model thinks

In the model picker is a row Effort, with the levels Off, Low, Medium, High, Extra high and Max. Per model only the levels that model really knows are offered, with a line underneath when something is missing, for example "Extra high and Max do not exist on Gemini" or "This model only knows thinking on or off." The level that is the model's own default is marked Default.

Switch to a model that does not support your current level and it visibly falls back to the nearest one that does exist, with the message alongside. Nothing quietly different from what it says is ever done.

A different Effort level also invalidates the cache, and there too the amount is shown.

What it costs

The header of a conversation shows the token usage and an estimate of the costs, based on the price table in the app. If the conversation runs on your own endpoint, only the token usage is there: the app does not know those rates, and inventing an amount would be worse than showing none. What one turn cost exactly, and what did and did not go along, is under the answer itself; see Conversations.

Across your whole usage you look in Statistics in the sidebar: activity, token usage over time, consumption per model, and how often your skills, personas and sources were brought in. Further down is what went wrong - failed tools, turns without a final answer, truncated answers, refused actions - broken down per model and per mode, plus how often your stored memories and approved skills were actually used. With every counter it says from when it has been measured; a low number is not automatically a good score.

Helper models for side jobs

Not everything has to be done by your main model. Inventing a title, summarising a long conversation or judging a suggestion are side jobs, and by default they run on a cheap model from the same provider. Under Settings → General → Helper tasks you set a different model per task:

  • Model for title generation - the title of a new conversation.
  • Model for skills review - checks after a turn whether there was a reusable lesson in it. This is also the pass that looks at your memory. See Skills.
  • Model for sub-agents - subtasks the assistant farms out.
  • Model for context compression - summarises the oldest turns of a long conversation. See Conversations.
  • Model for smart approval - judges agent actions in the "Approve smartly" setting. See Agent mode.

Automatic means, for four of the five, the cheap model of the provider of your conversation; with sub-agents it means the model of the conversation itself, because that is real work and not a side job. If you run locally, "automatic" is simply your own model: there is no separate local helper model, and local is free anyway.
