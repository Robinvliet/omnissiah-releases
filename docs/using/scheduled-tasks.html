Working with Omnissiah

Scheduled tasks

A scheduled task is an instruction that runs by itself: every morning, every weekday, once next week. You find them through Scheduled tasks in the sidebar.

A task consists of three things: a name, a schedule, and the instruction every run carries out. That instruction runs in a task conversation of its own, always in agent mode. The dialog says why that matters: "A scheduled task runs automatically in its own task conversation in Agent mode. Write the instruction so it stands on its own: the task knows no other conversations."

Making a task

Click New task and fill in:

  • Name. Short; it appears in the list and becomes the title of the task conversation.
  • Instruction. "Every run starts with this instruction as a message in the task conversation." So write it to be readable on its own, as if you were handing it to someone who knows nothing else.
  • Schedule. A dropdown with Daily, Weekdays, Weekly, Hourly, Once, Every X minutes and Cron expression, with the matching field next to it: a time, a weekday, a date, a number of minutes or the expression itself. Right below it you see what you chose: "Next run: Aug 19, 09:00 AM", or the reason the schedule is not valid yet.
  • Model and Approval. Both apply to the task conversation. The approval level works exactly as in an ordinary agent conversation; see Agent mode.
  • Fallback model. Optional, and off by default ("No fallback"). "Runs the task when the task model fails for good; the run reports that in the task conversation." Useful for a task that has to keep running when your usual provider is having a bad day; the task model itself never changes along with it.

Times are read in the time zone of the machine where Omnissiah runs, and that is your own machine.

One thing to know about Every X minutes: the interval is counted from the end of the previous run, while the app checks for due tasks once a minute. So "every minute" is in practice roughly every two minutes, and the longer the interval, the smaller that difference gets. Cron expressions do not have this: they are tied to the clock rather than to the previous run.

Or just ask in a conversation

You can also ask the assistant to schedule something. It translates your sentence into a schedule itself and makes a proposal that pauses until you approve it, just like with a skill. The task then inherits the model, the approval level and the project of the conversation you asked it in; adjusting comes afterwards in the overview.

This tool is called Schedule tasks in the list behind the + on the input bar, and you can switch it off there per conversation.

What you get back

When a run finishes, a counter appears at Scheduled tasks in the sidebar and a notification: "Scheduled task "Morning briefing": run succeeded", with a View button. The counter fades as soon as you visit the tasks page.

The page of a single task shows the schedule, the next run, the last status and the instruction itself, with the list Runs underneath. At the top are Task conversation (jump to the conversation), Run now ("Run started - the outcome appears in the task conversation"), and in the menu Edit, Pause or Resume, and Delete.

Every run has a status:

  • succeeded - the run finished.
  • failed - something went wrong; the reason is stated.
  • silent - the run ran and had nothing to report. See below.
  • awaiting approval - the assistant wants to do something you have to say yes to first. You do that in the task conversation.
  • skipped - this run did not happen, with the reason.
  • running - it is going on now.

If a run needed several attempts, that is shown on the row, and so is a fallback: "fell back to model".

In the task conversation

All runs of a task sit one after another in the same conversation, and that gets long. So the chat shows only the last run by default, with a pager at the top: Run 3 of 12, with the time next to it, arrows to previous and next, and Show all if you do want the whole history. Click a run in the run list and the conversation opens right on that run.

When a run says nothing

A task that summarises the news every morning does not have news every morning. In such a case the assistant answers with [SILENT], and then the run gets the status silent and the notification stays away. The turn is simply there in the task conversation, so you can always check that it ran.

That is also what the task is given in its instructions: it runs without a user present, asks no questions and waits for nothing, because its last answer is what you see later as the outcome. If it uses the protocol word and writes content anyway, the run row says "[SILENT] protocol violated" - a warning, not a status.

If the app was off

A scheduled task needs a running app. If your computer was off at nine o'clock, the morning briefing still runs as soon as you open Omnissiah again.

Piled-up missed runs do lapse: one is caught up, not five. That is visible as a skipped run with the reason: "Scheduled run of Aug 6, 09:00 AM was missed (the server was off); one catch-up run was made, earlier missed runs are dropped." A one-off task that has not run yet runs whatever time it is.

When a run is skipped

Two situations, and in both you see them in the run list instead of them happening quietly:

  • "The task conversation is in use right now; this run was skipped." You are working in that conversation yourself.
  • "The previous run is still waiting for an approval in the task conversation." As long as that is open, no new turn can go over it. Approve or reject it, and the schedule picks up again by itself.

In both cases the task moves on to its next moment.

If something goes wrong

A failed run does not fall away quietly. In the task conversation a message appears starting with "The scheduled run could not be completed:", with the reason behind it, and the run list shows the same reason.

Not every failure is final. A run that fails cleanly on something temporary - a rate limit, a provider that is briefly unreachable - is retried within the same run, up to three attempts, waiting longer each time. Work that was already done is never blindly repeated.

If it goes wrong three times in a row, the task pauses itself and says so: "The task was paused after 3 failed runs in a row." A broken task should not keep running for weeks. Fix the cause and you switch it on again with Resume.

Where scheduled tasks do not exist

In a project with Answer only from the sources you cannot create tasks and existing ones do not run: they work in agent mode, and that does not exist there. See Projects. If the task was already there before you turned that switch on, it pauses itself instead of failing again every time.

A scheduled run never creates new scheduled tasks itself. That is not left to the good will of the model: the tool is simply not in there during a run.

Deleting, finally, removes the task, not your work: "The task conversation with the earlier runs simply stays."
