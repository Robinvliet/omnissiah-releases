Working with Omnissiah

Skills

A skill is a piece of instruction you keep and use again. The page sums it up: "Skills are reusable instructions. Attach one to a message with / in the composer; the model can also load one itself when the description fits." You find them behind Skills in the sidebar; that button takes you to the page Skills.

Unlike a persona, a skill replaces nothing: it comes on top of what is already there, and you can attach several to one message. A skill reaches the model in two ways: you attach it to a message yourself, or the model picks it from the list on its own when the description fits your question. Nothing is switched on per conversation; a skill you attach belongs to that message and stays in the conversation history with it.

Where a skill lives

Every skill is a folder with a SKILL.md in it, in the skills/ folder of your data folder. That is ordinary markdown with a name and a description at the top, so you can just as well open it in your own editor. It is the same format Claude uses, so skills are interchangeable. See Data and backup.

Writing a skill yourself

Click Add skill at the top right and choose New skill. Then you fill in:

  • Name. "Lower case letters, digits and hyphens. This is also the folder name."
  • Description. "One line: what is this skill for?" That line does more work than you think, see below.
  • Instructions. The markdown the model gets. Write them as directions to the assistant.

Getting a skill from elsewhere

In the same Add skill menu are two other ways in:

Import… reads a SKILL.md file from your disk and opens it in the editor. Nothing is stored until you click Save.

From a URL… fetches a skill from the internet. You paste a GitHub folder ("github.com/anthropics/skills/tree/main/…") or the direct URL of a SKILL.md. Omnissiah fetches the skill, checks it over and puts it in the editor for review: where it came from, the files that came with it and what the scan found. Only then does the Install button appear.

If the scan found something, it is stated as a warning: "External skills are untrusted. Read the instructions above before you install." Installing then asks for an extra confirmation. A flag is a reason to look, not a lock; what exactly is scanned is on Privacy and security. Skills you fetch this way carry the label hub in the list, and the settings in their file (see below) survive the installation.

Attaching a skill to a message

Two ways in, and both do the same thing: they add a chip above the input bar for the message you are about to send.

  • Type a / in the input bar. A menu the width of the input bar appears with two sections: Commands (for now only Deep research) and Skills, each skill with its description and, in grey, where it came from. Whatever you type after the / filters the list; Enter or a click adds the skill and removes the / word from your text. At the bottom sits Manage skills…, which opens this page.
  • Click the + on the input bar and open the list Skills. It shows the same rows; a click adds the chip.

Every chip has a cross to take it off again, and you can combine skills with Deep research. There is a soft ceiling: "At most 5 skills per message." When you send, the chips go along with that message and the input bar is empty again. The sent message shows the skills it carried as chips at the top, and the action timeline of the answer says "Skill ‘name’ attached to the message". Edit that message, or retry the answer, and the same skills go along again.

Who may invoke a skill

For every skill you decide who may use it, in two layers.

The skill file carries the default. The same fields other tools use work here: disable-model-invocation: true (Claude Code) or allow_implicit_invocation: false in agents/openai.yaml (Codex) mean "only you", and user-invocable: false means "only the model". A skill fetched from elsewhere keeps its author's intent that way.

On the Skills page every skill has a picker next to it, Who may invoke. Follow the file is the default and states what the file says; the other four settings overrule the file: You and the model, Only you (/ menu), Only the model and Off. Off keeps the skill installed but offers it nowhere, which is the right setting for a skill you are still weighing. Skills only the model may use do not appear in the / menu; skills only you may use are not in the model's list.

One name is reserved: research is the command behind /research. A skill folder with that name gets a warning on the Skills page and cannot be attached with /; rename the folder.

What the model does with your skills

Not everything goes along every turn, and that is deliberate: skills that sit fully in the prompt cost room in every turn.

  • A skill you attached goes along with that message in full.
  • Its extra files (a references/ folder for instance) are in there only as a list of paths. The assistant reads one when the task calls for it.
  • Its scripts (a scripts/ folder) the assistant can run with the terminal tool, straight from the skill folder; the skill tells it the exact path, and the script runs in your linked folder or the conversation's workspace, under the approval level like any other command. The skill folder itself stays read-only for the assistant: to change a skill it proposes one, it never edits the folder directly, and a command that would write into or delete from the skills folder always pauses for your confirmation, whatever the approval level. A missing interpreter is just a failed command.
  • The skills the model may pick itself are in the prompt as an index: name and description, one line per skill. If one fits your question, the assistant fetches the full instructions itself.

That last part is why that one description line counts: it is the only thing the model can see whether a skill is relevant by.

If you run a local model that does not support tools, that fetching cannot happen. An attached skill then goes along in full including its extra files, and the index stays away: the prompt never promises something that is not there.

A skill attached to a message from long ago falls out of view when a long conversation is condensed: the summary keeps the gist, not the instruction. Attach it again if you still want it.

Skills that arise by themselves

Two things can propose a skill. With both, you approve, and until that moment nothing is stored.

The assistant, during a conversation. Ask for it, or ask repeatedly for the same kind of help, and it can propose a skill. That proposal appears in the chat and waits for Approve or Reject. That happens through a tool called Propose skills; it is always available and every proposal waits for your approval, so there is nothing to switch off. A skill that came into being this way carries the label assistant in the list; the ones you wrote yourself say own, the ones you fetched say hub.

A helper model, after a turn. That checks whether the conversation holds a reusable lesson - the same post-turn review that also looks at your memory. Such proposals pile up under Proposals from conversations on the Skills page, with a counter on the button in the sidebar: "The assistant saw a reusable lesson here. Nothing is saved until you approve." Per proposal the reason is stated, with a quote from the message it rests on, and with View text you can read the whole skill first.

If you do not want that, switch Self-learning skills off under Settings → General → Helper tasks. Which model does this you set there too; see Models.

Skill and memory proposals share one ceiling per conversation - Suggestions per conversation, 3 by default. Once that is reached the review stops for the rest of that conversation, even if there was more to learn. Approving does not free up a slot: the ceiling counts every proposal that was made, whether you approved it or rejected it.

A scheduled task makes no proposals at all: a run without anyone watching would only pile them up.

Editing and deleting

Click a skill in the list to open it, or use the pencil. Below the instructions the editor lists the files in the skill folder, such as a references/ or scripts/ folder; the assistant can run the scripts from the skill folder, see above. Deleting asks for confirmation and is final: "This cannot be undone." The folder disappears from your disk, so your backup is your only way back.

When a skill file is not in order

The list tells you. A folder without a SKILL.md, a name that is not a valid skill name, a missing description, an empty set of instructions: each is stated under the skill, and a skill that cannot be used at all is greyed out until you fix the file. Unknown fields in the file are never a problem; skills written for other tools keep working here.
