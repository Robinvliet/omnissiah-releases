Working with Omnissiah

MCP servers

Through Settings → Tools you link MCP servers that give the model extra tools, for example access to a file system, git or an external service. A server you switch on there joins every conversation. The page says it in one line: "MCP servers give the model extra tools: remotely over HTTP/SSE, or locally over stdio (a command that runs as a process each turn). A server you switch on here joins every conversation."

There are two flavours.

Remote (HTTP or SSE)

A URL, optionally with an Authorization header. The server runs somewhere else; Omnissiah only talks to it.

Local (stdio)

A command that Omnissiah starts as a process at the beginning of a turn and shuts down again afterwards. This is the most common type for personal use: the official servers for files and git, among others, are stdio.

Example: command npx, arguments -y @modelcontextprotocol/server-filesystem /path/to/folder. Environment variables, a GITHUB_PERSONAL_ACCESS_TOKEN for instance, you fill in as lines NAME=value; those values stay server-side and cannot be read back anywhere in the app.

What you should know before you add one

The command runs on the machine where Omnissiah runs, with the rights of your own account. Registering a stdio server is configuring a local command. Only add servers you trust.

As a safety net Omnissiah checks npx and uvx packages against the OSV database for known malware before starting. Only confirmed malware blocks, and the check is fail-open on network trouble: it is an extra pair of eyes, not a lock.

Bare commands are found. npx and the like also work when the desktop app was started with a minimal PATH; Omnissiah also looks in the Homebrew, /usr/local/bin and ~/.local/bin locations. If it still does not work, use an absolute path to the command.

In the Docker web version the command runs inside the container. npx is present there, because the container runs on a Node image; uvx and Python servers are not.

The child process gets a clean environment. Only PATH, HOME and similar basics plus what you supply yourself. Your API keys from .env do not leak into it.

Adding is a test

The button is called Add (test connection) for a reason. Omnissiah first connects and fetches the tool list; if that fails you get the reason and nothing is stored. So you never have a server in your list that turns out mid-conversation not to work.

The list shows per server what you filled in: the URL or the command with its arguments, and whether an auth header or environment variables belong to it. The values themselves are not there; those cannot be read back after saving. A server that is switched off is shown as switched off under Connections in the Command Center - not as a fault, because it is not broken, it simply is not taking part.

Switching a server on and off

Each server in the list has its own switch, and it applies to the whole app: on means the server joins every conversation, off means it is not contacted at all. There is no per-conversation choice any more, and no switch per individual tool.

Next to the switch the row says what the server costs: something like 2 tools · ~4,200 tokens per turn. That is an estimate of what its tool definitions take up in the prompt of every turn, whether or not the model actually calls them - which is exactly why the switch is worth using when a server brings many tools. The tilde is honest: it is a calculation on characters, not a tokeniser. The number is measured when you add the server; Measure again in the row menu refreshes it.

A server that is switched off keeps its last measurement, so you can see what turning it back on would cost.

What you see in a conversation

When the assistant calls a tool from a server, that step appears in the action timeline with the name of the tool and a small label with the server name next to it, so you see where it comes from. Behind the scenes they carry a longer name, mcp__<server>__<tool>, so that two servers with a tool of the same name do not get in each other's way.

A call that has given no answer after five minutes is aborted, with the message that the server sent nothing back within that time. Without that limit one slow server would leave your whole turn hanging.

Approval

Tools from MCP servers fall under the approval level of that conversation, just like writing files and the terminal, and they do so in every conversation. See Working in a folder.

That last part changed: until version 0.21.0 an MCP tool ran without asking in a chat or research conversation, because the approval levels only existed in agent mode. Now there is one lane and one consent layer, so a server you switch on is subject to your approval level everywhere.

One difference is worth the trouble: in the Approve automatically setting an MCP tool only goes through without asking if the server marks it as read-only itself. Everything else pauses. That is deliberately cautious, because that marking comes from the server and you did not write it.

When a server does not work

A server that will not connect at the start of a turn is skipped. The turn simply goes on, with the tools of the servers that do work, and you see it in the chat: above the answer it says "1 server unavailable", and if you unfold that block, the name of the server with the reason behind it. That message belongs to that answer and therefore stays with it after a reload.

The assistant gets exactly the same message in its instructions, plus the note that the turn continued with the tools of the servers that did work. It can therefore say that it could not reach something, instead of answering confidently from an incomplete picture. One broken server never stops the turn; it is only no longer kept quiet.

The reason is the error message of the server itself, shortened and with any keys filtered out. If it says too little, the full error is in the server logs. What the assistant did get from other servers stands apart from that.
