Working with Omnissiah

Working in a folder

Link a folder to a conversation and the assistant can work in it: look around, read files, and if you allow it, write, run commands and run scripts. There is no mode to switch on for this; what it may do follows from three things you can see - whether a folder is linked, whether that folder is read-only, and the approval level.

With tools it works in several steps in a row: plan, use a tool, look at the result and carry on. Twenty steps per turn at most.

First link a folder

You link one with Work in a folder in the bar under the input bar, or with Add folder in the menu next to it. What you get to see before you confirm is on Sources.

Only with a folder do the tools View folder, Read file, Write file, Terminal and Script exist. Without one, the conversation simply has no way to reach your disk.

You can link several folders at once. Every folder has a name, and in the action timeline you see per step which folder it happened in.

The terminal only works on macOS and Linux. On Windows the assistant says so and falls back to the file tools.

Read only, or read and write

Next to the folder chips sits a second setting, and it is the one that decides whether anything on your disk can change:

  • Read and write. "The assistant may edit files and run shell commands in the linked folders, under the approval level."
  • Read only. "The assistant can read the linked folders but cannot change anything: no file edits, no shell, no scripts."

Reading is always allowed once a folder is linked. On Read only the writing tools are not narrowed but absent: they are not in the turn at all, so there is nothing to approve and nothing to go wrong, and the same holds for a sub-agent the assistant farms work out to. A new conversation starts on read and write; conversations from before this setting kept exactly the permission their old mode gave them.

What happens without asking

Next to the + on the input bar sits the approval level. There are four settings, and they apply per conversation:

  • Approve manually. "The agent pauses so you can approve every action." This is the default.
  • Approve automatically. "The agent works on its own and only pauses for something risky."
  • Approve smartly. "A helper model reviews every action and only pauses what it does not trust."
  • Skip approvals. "The agent never pauses, not even for risky actions."

The level applies to writing files, the terminal, scripts and tools from MCP servers, in every conversation. Things that only land in the app itself, such as putting something in your sources or your memory, fall outside it.

When the assistant pauses, the proposed action appears in full in the chat, with the line that nothing is saved until you approve, and two buttons: Approve and Reject. There is no "always allow"; that is what the levels above are for.

An identical call you already approved in this conversation does not pause a second time. The timeline says so on that step, so an action that goes through without a question is never silent about why.

If the assistant delegates a subtask to a sub-agent, every action that needs approval is automatically refused there, and that is stated in the summary you get back.

Two safety nets that always run

They work in every setting, including Skip approvals.

Before a file is overwritten Omnissiah keeps the old version. Under that step you then find Restore, and afterwards: "Restored to the version from before this change." At most twenty versions per file are kept, for thirty days, and only for files up to 10 MB. If a file is too large for such a copy, the Automatic level pauses for the overwrite after all.

Before the first far-reaching command of a turn Omnissiah takes a snapshot of the whole working folder. Restoring asks for confirmation, and that dialog says exactly what happens: "Files created after the snapshot stay. Before restoring, the current state is captured too, so the action is reversible."

Documents are not overwritten with text

Word files, spreadsheets, PDFs and images are containers, not text. Writing plain text over one of them produces a file that no longer opens. That is now refused, in every approval setting, before the safety net above even comes into play: "Refusing to write plain text over …: the existing file contains binary data."

The message also says what does work: change such a document with a library through the terminal or a script, for example python-docx or openpyxl, or delete the file first to replace it entirely. Creating a new file is never refused; there is nothing to destroy yet.

What never goes through

Some commands are refused unconditionally, in every approval setting, and no setting lifts that. Think of formatting a file system, recursively deleting a system folder or your home folder, shutting the machine down, and writing to the database or the .env of Omnissiah itself. The message says the assistant should not try again and should not work around it either. If you really want such a thing, you run it yourself in your own terminal.

If your API keys happen to end up in the output of a command, a placeholder takes their place - [GEMASKEERD], one of the few strings that is still Dutch - and the child process does not get them in the first place.

Be honest about what this is

Those safety nets and levels prevent accidents; they are not a security boundary. The real boundary is your operating system. So do not link a folder whose contents you would not want to lose without a backup. More about that is on Privacy and security.

Where changing things does not exist

In a project with Answer only from the sources nothing on your disk can change, and scheduled tasks cannot run either. Reading a linked folder is still allowed there, and it is even one of the ways an answer gets its source reference. What falls away is writing, the terminal, scripts and sub-agents: those produce content that is not a source, and the promise could then no longer be kept. See Projects.
